# 04: A Visible Part, and a visible Vendor with its Offers, through the API

**Spec:** [the browse spec](../spec.md)

**What to build:** Anyone, with no Login, can ask the API for three things:

- a Visible Part, with its specifications labelled in English;
- an active Vendor's name, city and Contact details;
- one page of an active Vendor's Visible Offers, grouped by Category, each with its Part and its Shown Price in the chosen currency.

A Part that is not visible, and a deactivated or unknown Vendor, answer 404, so the Shopper app can show its not-found page. With `GET v1/parts/{partId}/offers`, which `pricing` left, these are everything a Part page and a Vendor page read.

**Blocked by:** 02

**Status:** resolved

- [x] **A Visible Part.** `GET v1/visible-parts/{partId}`, marked `@Public()` and described with `security: []`. It answers the Part's identifier, Category, name, manufacturer, part numbers, photo's path and specifications. It reads ticket 02's rule for a Visible Part, not a copy of it. A Part that is not visible, or unknown, is answered 404 with `NOT_FOUND`. A malformed identifier is answered as the Part read for the Admin answers one.
- [x] **Its specifications.** Answered in the order of the Category's specification list, each with its English label, its value and its unit. A specification the Part does not hold is left out. So is a stored 0 that the list says means "not known". Yes-or-no values are booleans. A Part is visible by the same rule as everywhere: an Admin's or a Vendor's token gives no more.
- [x] **A visible Vendor.** `GET v1/visible-vendors/{vendorId}`, public in the same way. It answers the Vendor's identifier, name, city, address, map location, phone number, WhatsApp number, Instagram name and opening hours, with null for each detail the Vendor has not given. It never answers the Login phone number, whether the Vendor is active, or when it was made or changed. A deactivated or unknown Vendor is answered 404 with `NOT_FOUND`.
- [x] **A visible Vendor's Offers.** `GET v1/visible-vendors/{vendorId}/offers` with `currency`, which is required and refused as `GET v1/parts/{partId}/offers` refuses it, and `page` and `size` through `PagingRequest`. Each Visible Offer has its Part's identifier, Category, name, manufacturer and photo's path, and its Quoted Prices, Shown Price, in-stock status, warranty and days since Confirmation, as a Part's Visible Offers answer them. A deactivated or unknown Vendor is answered 404.
- [x] **Their order.** Grouped by Category in the catalog's fixed order of the eight. Within each Category, OFF-11's order: in stock first, then the lowest Shown Price, then the most recent Confirmation, then the Part's name, then the Offer's identifier. Paging runs across the groups.
- [x] **One snapshot.** The visible-Offer rule is read through `visibleOffer(now)` and the Shown Price through `pricing`'s SQL expression. The Platform Rate is read in the same query as the Offers.
- [x] `pnpm api-client:write` is run, and the description and the client are committed.
- [x] `pnpm integration:check` gains these tests, written before the code, and passes:
  - A Part whose only Offer is an Expired Offer, one whose only Vendor is deactivated, and an unknown Part answer 404. Confirming the Offer again or reactivating the Vendor brings the Part back.
  - A Visible Part's specifications are in the list's order, with labels and units, leaving out what it does not hold and a 0 that means "not known".
  - A visible Vendor answers its contact details, with null where one is not given. Its answer holds no Login phone number. A deactivated and an unknown Vendor answer 404, with their Offers as well.
  - A visible Vendor's Offers leave out its Expired Offers. They are grouped in the catalog's order of Categories, and in OFF-11's order within each, in each currency.
  - An Admin's or a Vendor's token changes nothing in any answer.
- [x] Each of these is shown once and then reverted, and each fails its own test: a deactivated Vendor's page answered; a "not known" 0 answered as a specification; the Offers ordered by price across Categories instead of within them.
- [x] `pnpm check` passes with Docker stopped.
- [x] The results of the fault checks are recorded under Comments.
- [x] The work is committed in pieces, each leaving `pnpm integration:check` and `pnpm check` passing.

**Decisions this ticket left open.**

- **A Visible Part's read** is the Offer Store's `readVisiblePart(partId, now)`, which asks ticket 02's `visiblePart(now)` of `part` by its identifier, in one statement with its photo; nothing of the rule is written again. `ReadVisiblePartQuery` is in `domain/offer`, beside `ListVisiblePartsQuery`, and answers a Part that is not visible, an unknown one and an identifier of no Part with `PART_NOT_FOUND` (404, `NOT_FOUND`), as the Admin's read answers an identifier of no Part. The endpoint is `VisiblePartController`, in `visible-part.controller.ts`, a controller of its own so that ticket 03's additions to `VisiblePartsController` do not meet it. It is listed after `VisiblePartsController` in `OfferModule`, because Nest matches the routes in the order of the controllers: `v1/visible-parts/filters` (ticket 03), declared in `VisiblePartsController`, comes first and is never taken for a Part's identifier.
- **The labelled specifications** are the domain's: `Specification.labelled(value)`, `SpecificationList.labelledIn(document)` and `Part.getLabelledSpecifications()`, answering `LabelledSpecification`s, in `domain/specification/LabelledSpecification.ts` with `LabelledRows`. Whether a Part holds a specification is `Specification.isMissingIn`, the one rule for what is missing, which `missing-specifications` and a Part's own `missingNeededSpecifications` also read, so a stored 0 where the list says 0 means "not known" is left out with nothing, null, an empty text and an empty choice; a 0 where 0 can be true, a CPU's efficiency cores, is answered. A value is answered as stored: the checks before storing make yes or no a boolean. A list of rows answers its rows, each the fields it holds, labelled the same way in the order of the list's fields, and no rows as `[]` (a motherboard with no M.2 slot); something stored for rows that is not a list, or a row that is not an object, is left out.
- **The answer** is `VisiblePartWithSpecificationsResponse`, the catalog's `PartSummaryResponse` with `specifications`, each a `LabelledSpecificationResponse`: `path`, `label`, `kind`, `unit` (null when it has none) and `value`, described as one of a number, a text, a boolean, a list of texts or a list of rows of `LabelledSpecificationResponse`, which the client types as `number | string | boolean | Array<string> | Array<Array<LabelledSpecificationResponse>>`. `path` and `kind` are beyond the ticket's label, value and unit: `path` names a specification as the Category's list and the filters do, and gives the page a key; `kind` says how to word a value and tells an empty list of rows from anything else. The factory is `static override of`, as `noImplicitOverride` asks.
- **A visible Vendor** is read by `ReadVisibleVendorQuery`, in `domain/vendor`, through `VendorStore.readById` and `Vendor.isActive()`: a deactivated Vendor, an unknown one and an identifier of no Vendor are answered `VENDOR_NOT_FOUND`, whoever asks. A Vendor with no Visible Offer is answered, so that its page still says how to reach it (story 53). The endpoint is `VisibleVendorsController` in `VendorModule`. Its answer, `VisibleVendorResponse`, holds the nine details, null for each one not given; the Admin's `VendorResponse` now extends it with the login phone number, `active`, `createdAt` and `updatedAt`, so that the contact details are described once, and its schema in the description is unchanged.
- **A visible Vendor's Offers** are the Offer Store's `listVisibleByVendor(vendorId, currency, pageable, now)`, answering `Option<VisibleOffersOfVendorPage>` (in a file of its own), and `ListVisibleOffersOfVendorQuery`, which answers none with `VENDOR_NOT_FOUND`. **It is one statement**: a CTE `listed` holds the Vendor's Offers by `visibleOffer(now)`, each with `shownPriceIn` at the current rate, left-joined once (`currentPlatformRate(client)`), and its `row_number()` in the order of a Vendor's Offers; `counted` holds their total as one row; the answer selects the Vendor's row by its identifier and `active`, joined to `counted` and to the page's places of `listed`, its Offers, Parts and photos. No row means the Vendor is deactivated or unknown; one row with no Offer, an empty page with its total. So the Vendor's activity, the rate, the Shown Prices, the order, the page and the total are of one snapshot. The aliases (`listed_offer_id`, `shown_amount`, `shown_converted`, `place_in_list`, `total`) are names no table in the statement has as a column, as ticket 02's note asks.
- **The order.** `inOff11sOrder(shownAmount)` names OFF-11's order once at the Store's module level: in stock first, the lowest Shown Price as answered with none after the others, the most recent Confirmation. `inTheOrderOfAPartsOffers` is it, then the Vendor's name and the Offer's identifier, as before; `inTheOrderOfAVendorsOffers` is `placeOfCategory(part.category)` first, then it, then the Part's name and the Offer's identifier. The answer is one list across the groups, and paging runs across them; each Offer's `part.category` tells the page where a group starts.
- **Each Offer of a Vendor's** is `VisibleOfferOfVendorResponse`: `part` as the catalog's `PartSummaryResponse`, as `OfferResponse`'s is, which also carries `partNumbers`, beyond the ticket's list; and both Quoted Prices, `shownPrice`, `inStock`, `warrantyMonths`, `confirmedAt` and `daysSinceConfirmation`, now in `VisibleOfferDetailsResponse`, which a Part's `VisibleOfferResponse` extends with its `vendor`. That moves `vendor` to the end of a Part's Offer, in the JSON and in the generated type; nothing else of it changed. The page is `VisibleOfferOfVendorPageResponse`, through `PagingResponse`; the request, `ListVisibleOffersOfVendorRequest`, takes `currency` as `ListVisibleOffersOfPartRequest` does, with `PagingRequest`'s `page` and `size`.
