# 02: A Category's Visible Parts through the API

**Spec:** [the browse spec](../spec.md)

**What to build:** Anyone, with no Login, can ask the API for one page of a Category's Visible Parts in the chosen currency. Each Part comes with its Lowest Price, the lowest Shown Price among its in-stock Visible Offers, marked when that price was converted. It also comes with how many Vendors offer it and whether any of them has it in stock. The Parts are in BRW-1's order: by Lowest Price, lowest first, with Parts that every Vendor has out of stock last. The list can be searched by name, manufacturer and part number, with the catalog's own word rule. The rule for which Parts are visible is written here once, for every later endpoint. No Shopper page reads the list yet; the integration tests prove it.

**Blocked by:** None (can start immediately)

**Status:** resolved

- [x] **The words.** Visible Offer, Visible Part and Lowest Price are added to CONTEXT.md before any code uses them, as the spec defines them, each with the words to avoid. A Visible Offer goes under Vendors and offers, a Visible Part under Catalog, and the Lowest Price under Prices.
- [x] **The rule for a Visible Part.** A Part with at least one Visible Offer. It is written once as SQL at the Store's module level and reads `visibleOffer(now)`, so that ticket 04 and `builder` reuse it. It is not written a second time.
- [x] **The endpoint.** `GET v1/visible-parts` with `category`, `currency`, `search`, `page` and `size`. It is marked `@Public()` and described with `security: []`, and it answers the same with a good token, a bad one or none. `category` and `currency` are required. A missing or unknown value is refused with 400, `NOT_VALID`, naming the field.
- [x] **The answer.** The catalog's page shape, through `PagingRequest`. Each Part has its identifier, Category, name, manufacturer, part numbers and photo's path. It also has `lowestPrice`, shaped as `shownPrice` is (`{ currency, amount, converted }`) or null, the number of Vendors with a Visible Offer for it, and whether any Visible Offer is in stock.
- [x] **The Lowest Price.** It is the lowest Shown Price among the Part's in-stock Visible Offers, compared as answered, after rounding. It uses `pricing`'s SQL expression for a Shown Price, and the Platform Rate is read once, in the same query as the rest. It is null when no Visible Offer is in stock, and when no in-stock Offer has a Shown Price because there is no Platform Rate.
- [x] **The order.** Parts with a Lowest Price come first, lowest first. Then in-stock Parts with none, which happens only with no Platform Rate. Then Parts whose Visible Offers are all out of stock. Ties go to the name, then the identifier.
- [x] **The search.** It uses the catalog's word rule, not a copy of it: every word, in any order and any case, in the name, the manufacturer or a part number. An empty search finds every Visible Part.
- [x] `pnpm api-client:write` is run, and the description and the client are committed.
- [x] `pnpm integration:check` gains these tests, written before the code, and passes:
  - A Part with no Offer is not listed. Neither is one whose only Offer is an Expired Offer, nor one whose only Vendor is deactivated. Confirming the Offer again, or reactivating the Vendor, lists it.
  - Only the asked Category's Visible Parts are listed.
  - The Lowest Price ignores out-of-stock Offers and Offers that are not Visible Offers. It is marked converted exactly when the Offer it comes from was converted, in each currency.
  - The order is as stated above. The same Parts can be in another order in the other currency.
  - The number of Vendors counts Visible Offers, in stock or not, and nothing else.
  - The search finds by name, by manufacturer and by part number, with words in any order and any case.
  - Paging answers the page's size and the total, as the catalog's paging does.
  - An Admin's or a Vendor's token changes nothing in the answer.
  - A missing or unknown `category`, and a missing or wrong `currency`, are refused, each naming its field.
- [x] Each of these is shown once and then reverted, and each fails its own test: an out-of-stock Offer counted in the Lowest Price; an Expired Offer making a Part visible; the Platform Rate read in a second query; the order by Quoted Price in place of the Shown Price.
- [x] `pnpm check` passes with Docker stopped.
- [x] The results of the fault checks are recorded under Comments.
- [x] The work is committed in pieces, each leaving `pnpm integration:check` and `pnpm check` passing.

**Decisions this ticket left open.**

- **Where it lives.** The rule and the list are in the Offer Store, `DatabaseOfferStore.ts`, beside `visibleOffer(now)`, `shownPriceIn` and `inTheDatabase`, which stay private to that module: the MVP spec says `browse` reads visible Offers "with a Store method of their own", and no query for Shoppers reads `offer` another way. The domain has `VisiblePart` (the Part, its Lowest Price as a `ShownPrice` or null, `getVendorCount()`, `isInStock()`) and `ListVisiblePartsQuery` in `domain/offer`, beside `VisibleOffer` and `ListVisibleOffersOfPartQuery`, and the port gains `listVisibleParts(ListVisiblePartsParams)` answering a `VisiblePartsPage`. The endpoint is `VisiblePartsController` in `infrastructure/offer/endpoints/visible-parts.controller.ts`, in `OfferModule`, as `PartOffersController` is, with `ListVisiblePartsRequest`, `VisiblePartResponse` (which extends the catalog's `PartSummaryResponse`) and `VisiblePartPageResponse`.
- **The rule for a Visible Part** is `visiblePart(now)`, at the Offer Store's module level: `exists (select 1 from offer join vendor … where offer.part_id = part.id and visibleOffer(now))`, a condition asked of `part`. Ticket 04's read of one Visible Part and ticket 03's filter values can ask it of `part` as it stands, and `builder` the same.
- **The list is one statement.** A CTE `listed` holds every Visible Part asked for (the Category, `holdingEveryWord(words)` and `visiblePart(now)`), with the current rate left-joined once (`currentPlatformRate(client)`), a lateral subquery `offered` of what its visible Offers say of it, and `row_number()` in the list's order as `place_in_list`. The answer selects from `counted`, the total as one row, left-joined to the page's places of `listed`, so that a page past the end still answers the total, all in the one statement. The rate, the Lowest Prices, the order, the page and the total are therefore of one snapshot; the catalog's two reads in one transaction were not used, since a second read would read the rate a second time.
- **What its Offers say of a Part** (`offered`): `count(*)`, which is the count of Vendors since a Vendor has one Offer for a Part at most; `coalesce(bool_or(in_stock), false)`; and the Lowest Price, the Shown Price of the first in-stock visible Offer in OFF-11's order, `(array_agg(… order by inTheOrderOfAPartsOffers(…)) filter (where in_stock))[1]`, for its amount and for its `converted`. In stock first and then the lowest Shown Price makes it the lowest in-stock Shown Price, compared as answered, after rounding; of equal ones it is the one a Part's own Offers list first (the most recent Confirmation, then the Vendor's name, then the Offer's identifier), so it is marked converted exactly when that Offer's Shown Price is. It is null when no visible Offer is in stock, and when the first in stock has no Shown Price, which happens only with no Platform Rate. `offered` describes a Part and never decides whether it is listed; `visiblePart(now)` alone decides that.
- **The order** is `lowest_amount asc nulls last, any_in_stock desc, part.name asc, part.id asc`: a Lowest Price first, the lowest first; then in-stock Parts with none; then all out of stock; then the name and the identifier.
- **Drizzle names a subquery's field by its alias alone** (`"vendor_count"`, not `"offered"."vendor_count"`), so the aliases (`vendor_count`, `any_in_stock`, `lowest_amount`, `lowest_converted`, `visible_part_id`, `place_in_list`) are names no table in the statement has as a column; the comment in the Store says so for whoever adds a field.
- **The answer** is the catalog's page shape through `PagingRequest` and `PagingResponse`: each Part's `id`, `category`, `name`, `manufacturer`, `partNumbers` and `photoPath`, with `lowestPrice` (`ShownPriceResponse`, `{ currency, amount, converted }`, or null), `vendorCount` and `inStock`. `category` is `@IsIn(Category.keys())` and `currency` `@IsIn(currencies)` with the enum named `Currency`, both required; `search` is optional, read by `searchWordsOf` and found by `holdingEveryWord`, the catalog's own.
- **For tickets 03 and 04.** The price range and the filters go into `ListVisiblePartsParams` and the `where` of `listed`; a range on the Lowest Price can be a condition on `offered.lowestAmount` there, in the same statement. A Visible Part's own read asks `visiblePart(now)` of `part` by its identifier.
