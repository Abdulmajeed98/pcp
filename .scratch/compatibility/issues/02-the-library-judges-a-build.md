# 02: The library judges a Build: its seam, its public face and rules 1 to 7

**Spec:** [the compatibility spec](../spec.md)

**What to build:** The tracer bullet. `@pcp/compatibility` gets its test seam, the one the owner added on 7 November 2026, and its public face, and the first seven Compatibility Rules, the ones between a CPU, its cooler, its motherboard, its RAM and its case. Given a Build, the library answers the outcome of every rule that applies to it, in rule order, naming the Parts each outcome is about. A rule is unchecked only when a missing needed specification could change its outcome, and an unchecked rule is never passed. No caller uses the library yet: its tests are the proof, written before the code.

**Blocked by:** 01

**Status:** ready-for-agent

- [x] **The words.** CONTEXT.md gains two terms under Shoppers and builds, before any code uses them, each with the words to avoid. **Compatible**: said of a Part and a Build, when adding the Part to the Build would cause no Compatibility Problem; a Compatibility Warning or an unchecked rule does not make a Part incompatible (CMP-4). **Estimated power draw**: what a Build is reckoned to draw, its CPU's TDP plus its GPU's TDP, none without a GPU, plus 100 W for everything else (CMP-5). The wording may be bettered; the meaning is CMP-4's and CMP-5's.
- [x] **The seam.** Jest, as `core` has it: the workspace's Jest preset with SWC, a `test` target that `pnpm check` runs, the tests under the library's own `src/test`, and the test files' eight lint rules. The tests use Jest's globals and import nothing from Jest or any other package, since the library's ban on npm packages covers its test files. A helper that asserts is named in the lint rules' list of assertions. What the seam tests, and what it never does, is written where its tests live.
- [x] **The Build as the rules read it.** At most one each of CPU, CPU cooler, motherboard, GPU, case and PSU, and any number of RAM kits and drives, each with its quantity, at least one. Each Part carries an identifier the caller gives and its needed specifications in OpenDB's names and nesting, as the catalog holds them, with each one the catalog counts as missing left out. The library holds no copy of the catalog's rule for what is missing: a value it is given is known, and a value it is not given is missing.
- [x] **Judging a Build.** The library answers the outcome of every rule that applies (CMP-2), in rule order: the rule's number, its outcome (it passes, a Compatibility Problem, a Compatibility Warning, or unchecked), and the Parts it is about. For a Problem or a Warning those are the Parts whose values make it, every counted kit among them for a rule that counts. For an unchecked rule they are each Part whose missing needed specification could change the outcome, with that specification's path.
- [x] **Unchecked only when it matters.** A missing value is taken to be any value its specification could hold, 0 among them. One outcome per rule: a Problem when the values present prove one; otherwise unchecked when a missing value could still change the outcome; otherwise a Warning or a pass, as the values say.
- [x] **Each rule stated once**, with its number, the Categories it involves, the specifications it reads in each and its judgment. From those statements the library answers each Category's needed specifications by their paths; the API reads them in ticket 06.
- [x] **Rules 1 to 7**, as the spec's table reads OpenDB's values: rule 1's "2 x \<socket\>" boards take a CPU of that socket and its "Integrated …" boards make any CPU a Problem; rules 3 and 4 judge each RAM kit; rules 5 and 6 count every kit's modules, and their capacity, times the kit's quantity; rule 7 fits a Thin Mini-ITX board where Mini-ITX fits and a Flex ATX board where Micro ATX fits.
- [x] The library's tests are written before the code, and they prove each of these:
  - for each of rules 1 to 7, every outcome it can have: it passes, it finds a Compatibility Problem, and it is unchecked;
  - rule 1's dual-socket boards and its boards with a CPU built in, an "Integrated …" board making a Problem of a CPU whose own socket is missing;
  - rule 7's Thin Mini-ITX and Flex ATX boards;
  - two of one kit count as two kits' modules and capacity in rules 5 and 6, as many modules as the board's slots pass and one more does not, and as much memory as the board's maximum passes and one more GB does not;
  - a Build without the Parts a rule involves gets no outcome for it, and an empty Build gets none at all;
  - unchecked only when it matters: of two kits, one whose type is missing and one whose known type the board does not take make a Problem naming the known kit and the board, while two kits of which the known one fits leave rule 4 unchecked, naming the other kit and its type; and a board whose slots are missing leaves rule 5 unchecked whatever the kits hold;
  - each outcome names the Parts it is about by the identifiers the caller gave.
- [x] Shown once and then reverted, each failing its own test: a missing socket read as a pass in rule 1; a kit's quantity ignored in rule 5.
- [x] `pnpm boundaries:check`, run on its own since the library gains a target and test files, passes.
- [x] `pnpm check` passes with Docker stopped, the library's tests among it.
- [x] The results of the fault checks are recorded under Comments.
- [x] The work is committed in pieces, each leaving `pnpm check` passing.

**Commits.** `959712a` adds the two terms to CONTEXT.md, before any code uses them. `f331ba1` gives the library its seam and its public face, with rule 1; `b2226ff` adds rules 2 to 4, `1ea1805` rules 5 and 6, and `8f806d3` rule 7 and the needed specifications. **The words.** CONTEXT.md, under Shoppers and builds, after Compatibility Warning: **Compatible**, said of a Part and a Build, when adding the Part to the Build would cause no Compatibility Problem, neither a Compatibility Warning nor an unchecked Compatibility Rule making a Part incompatible (avoid: fits, suitable, supported, valid); and **Estimated power draw**, what a Build is reckoned to draw, its CPU's TDP, plus its GPU's TDP when it has one, plus 100 W for everything else (avoid: power consumption, total TDP, wattage, load). Wattage and TDP stay the words for a PSU's and a Part's own specifications.

**The seam.** As `core`'s: `jest.config.cts` with the workspace's preset and SWC, its `.spec.swcrc` copied unchanged, a `tsconfig.spec.json` with Jest's and Node's types for the globals and the config file, `tsconfig.lib.json` leaving the tests out, and an `.oxlintrc.json` that extends the root's rules and the test files' eight, with the `jest` plugin. Nx infers the `test` target from the config, so `pnpm check` runs 32 tasks where it ran 31. The tests are under `src/test`: `judge-build.spec.ts`, `rules/rule-01.spec.ts` to `rule-07.spec.ts` and `needed-specifications.spec.ts`, 65 tests in 9 files. They use Jest's globals and import only the library's entry file and `outcomeOf`, a helper of their own that picks one rule's outcome from a Build's and asserts nothing, so the lint rules' list of assertions is unchanged. `src/test/README.md` says what the seam tests and what it never does. Shown once each on the committed tree and put back by the inverse edit: `import '@jest/globals';` at the top of `judge-build.spec.ts` failed the library's lint with "A project tagged with "scope:shared" is not allowed to import "@jest/globals"", so the ban covers the test files; and an `it.only` there failed it with `jest(no-focused-tests)`.

**The public face.** `judgeBuild(build)` answers a list of `RuleOutcome`: `{ rule, outcome, parts }`, the outcome `passes`, `problem` or `warning`, or `{ rule, outcome: 'unchecked', missing }`, each missing value `{ part, path }`. `neededSpecificationsOf(category)` answers a Category's needed specifications by their paths. The types it takes and gives are exported with it: `Build`, `Part`, `PartAndQuantity`, `Category`, each Category's specifications (`CpuSpecifications` and the rest), `RuleOutcome`, `MissingSpecification`, and each fixed set's values as a type beside its set in `fixed-sets.ts` (`Socket`, `RamType`, `MotherboardFormFactor`, `PowerSupplyFormFactor`, `StorageFormFactor`, `StorageInterface`, `M2SlotKey`). A Problem names the Parts whose values make it, every counted kit among them; a pass names every Part the rule judged; an unchecked rule names each missing value that could change its outcome. Parts come in the catalog's order of Categories, and kits and drives in the Build's order.

**The Build.** Its keys are the API's Category keys, `cpu`, `cpuCooler`, `motherboard`, `ram`, `storage`, `gpu`, `case` and `psu`: one Part of each, or a list of kits or drives. A Part is `{ id, specifications }`, and a kit or a drive also has its `quantity`. Each Category's needed specifications are typed in full, as the catalog holds them, the GPU's, the PSU's and a drive's among them though no rule reads them yet, and a cooler's `water_cooled`, which rule 17 will read, so that tickets 03 and 04 add statements without both editing these types. A value left out is missing, and nothing else is; the library does not check that a quantity is at least one.

**Each rule stated once.** In `src/rules/rule-01.ts` to `rule-07.ts`, listed in rule order in `rules.ts`, each as `rule({ number, involves, judge })`. `involves` maps each Category the rule involves to the paths it reads there, and the rule applies when the Build holds a Part of each. Its judgment is handed those Parts and reads each value through `read(path)`, typed from the statement, so a path not stated, or misspelt, fails the type check, and the value comes typed from its set. `neededSpecificationsOf` reads the statements: each Category's paths in the order the rules first read them.

**Unchecked only when it matters.** A judgment answers a finding of whether the Build has a Problem: it holds, about the Parts whose values decide it; it does not; or maybe, naming the missing values that could decide it. The findings are in `src/rules/findings.ts`. `whatever(reading, set, find)` takes a missing value to be each value of its fixed set, and leaves the finding open, naming the value, only when they disagree: an "Integrated …" board makes a Problem of any CPU, its socket missing or not. `includes` reads a list a Part holds; `some` judges each kit, and a kit that makes a Problem makes it whatever the others lack; `not` turns a finding round. Counts are amounts, `product`, `total` and `exceeds`: a missing count could be any number, 0 among them, so a total that holds one has no upper bound, and a known 0 makes a product 0 whatever the rest is. A value that several Parts' findings share is taken once, around them: rule 4 reads the board's type before the kits', since, stated kit by kit, it left two kits of different types unchecked under a board whose type is missing, though no board takes both. That test was seen failing so before the rule was put the other way round.

**Rules 1 to 7, test first.** The tests prove each outcome of each rule, each reading, the limits, the quantities, a rule that does not apply, an empty Build, and the cases of unchecked only when it matters that the ticket names, with three more of their kind: in rules 5 and 6, a Problem the known kits prove beside a kit whose count is missing names the known ones only; and in rule 4, two kits of different known types are a Problem under a board whose type is missing. Every test names its Parts by identifiers it gave, such as `a-ddr4-kit`, and every outcome names them so. Rule 7 was stated first without its two readings, and only the two tests of the shared mounting failed. Every test but five was seen failing before its code, for its own reason: the empty Build's and a lone CPU's with the library throwing as it read a Part the Build lacked, since every rule was judged then, and the rest on their assertions. The five passed when written, since the code already gave them: rule 1's two guards on its readings' edges, a "2 x LGA 2011-3" board refusing an "LGA 2011" CPU and an "Integrated …" board refusing a CPU of another socket, which plain inequality gave; and the needed specifications of the drive, the GPU and the PSU, none yet, which the empty stub gave.
