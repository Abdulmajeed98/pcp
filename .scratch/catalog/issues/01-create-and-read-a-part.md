# 01: Create and read a Part through the API, proven against a real PostgreSQL

**Spec:** [the catalog spec](../spec.md)

**What to build:** The Admin creates a Part through the API, giving its Category, name, manufacturer and part numbers, and anyone with a Login reads it back. A Vendor reads it too, and is refused when it tries to create one. This is the first time the platform stores anything.

It is the first path through every part the catalog needs. PostgreSQL is reached through Drizzle with `pg`, and the API gains its database settings. A first table is made by a first migration, generated from the schema. Domain code returns Effect's `Either`. `core` gains the structured errors that domain code returns. The first entity, Store, Command and Query are built in the shape ADR-0004 describes, for every later module to copy. The API's tests against a real PostgreSQL are run by a new command, `pnpm integration:check`, in a container that the tests start themselves.

A Part has no specifications yet (ticket 03), and there is no search (ticket 06) and no photo (ticket 07). Nothing here touches the development database. Ticket 02 applies the migrations there and runs the API against it.

**Blocked by:** None (can start immediately)

**Status:** ready-for-agent

- [ ] Before anything is written, these are read for the releases that will be installed, and the findings are recorded under Comments:
  - Drizzle's node-postgres driver and its migrator;
  - drizzle-kit's `generate` and its configuration;
  - Effect 3's `Either`;
  - Testcontainers' PostgreSQL module;
  - the workplace's documents on its layers, its errors, its Drizzle set-up and its tests. They are read, and nothing is copied.
- [ ] Drizzle ORM 0.45, `pg` 8, drizzle-kit 0.31, Effect 3 and Testcontainers 12 with its PostgreSQL module are added. A new package's install script is read before it is listed.
- [ ] The API has three new settings: `DATASOURCE_URL`, which defaults to the development database's address; `DATASOURCE_USERNAME`, which defaults to `pcp`; and `DATASOURCE_PASSWORD`, which has no default. The API refuses to start without the password, and its message names it. The test of the API's settings covers all three.
- [ ] The API connects only when a call needs the database. Its existing tests of its HTTP surface still pass in `pnpm check`, with Docker stopped.
- [ ] The Part table holds:
  - the platform's own identifier;
  - the Category, one of the eight keys that `i18n`'s shared terms use;
  - the name and the manufacturer;
  - the part numbers;
  - the OpenDB ID, which may be empty and is unique when present;
  - when the Part was created and when it last changed.
- [ ] The first migration is generated by drizzle-kit into the API's source tree, and its file name says what it does.
- [ ] `core` gains the structured errors that domain code returns, and the exception a controller raises from one. The existing filter turns that exception into the existing error body, with the error's own code. Domain and Store code never throws.
- [ ] The domain holds:
  - a Part entity with getters;
  - an abstract `PartStore`, which is the port;
  - `CreatePartCommand` and `ReadPartQuery`, each with its own Input and Output.

  The infrastructure holds:
  - the Drizzle schema;
  - `DatabasePartStore`;
  - the controller, with its Request and Response classes;
  - the module, which binds the port with the abstract class as its token.
- [ ] **Create.** The Admin creates a Part and the answer is the Part. Every value is checked:
  - The Category must be one of the eight.
  - The name and the manufacturer are required and may not be blank.
  - Part numbers are trimmed, empty ones are dropped, and duplicates are removed regardless of case, keeping the first spelling.
- [ ] **Read.** The Admin and a Vendor read a Part. A Part that does not exist is answered 404, with an error code of its own.
- [ ] **Refusals.** A Vendor's attempt to create a Part is answered 403. A call without a token is answered 401, for both endpoints.
- [ ] `pnpm api-client:write` is run, and the description and the client are committed.
- [ ] `@pcp/core/test-utils` gains a shared test database. It starts one `postgres:18.6` container for every test file, applies the committed migrations, and empties the tables between tests.
- [ ] The API's tests against it are `*.integration-spec.ts` files under its test tree, mirroring its source, and run by a target of their own. `pnpm integration:check` runs that target for every project that has one. It says so plainly when Docker is not running, and `pnpm check` does not run it.
- [ ] `pnpm integration:check` passes with these tests, which go through the API's HTTP surface with tokens from the Keycloak stand-in:
  - The Admin creates a Part and reads it back with every value as given, part numbers cleaned as above.
  - A Vendor reads it.
  - A Category outside the eight, a blank name and a missing manufacturer are each refused with an answer that names the field.
  - A Part that does not exist is answered 404 with its code.
  - A Vendor's create is answered 403, and calls without a token are answered 401.
- [ ] Shown once and then reverted, each failing its own test: the Vendor role added to create; the check on the manufacturer removed; the mapping of a missing Part to 404 removed.
- [ ] `pnpm check` passes with Docker stopped.
- [ ] The results of the fault checks are recorded under Comments.
- [ ] The work is committed in pieces, each leaving `pnpm check` passing.
