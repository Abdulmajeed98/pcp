2. **Every rule's every outcome checked against the library.** Fixed in `a269d57`, test first. Each rule states its number as written and, for rules 11, 15 and 20, `canWarn: true`, and its judgment is typed by it (`problemWhen` with a `warningWhen` only for such a rule), so a rule cannot find a Warning without saying so. The library answers `ruleNumbers` and `rulesThatCanWarn` from its own list and types `RuleOutcome` by them. The API describes each outcome as one of two schemas, `OutcomeOfARuleThatCanWarnResponse` (rule 11, 15 or 20; `passes`, `problem`, `warning` or `unchecked`) and `OutcomeOfAnotherRuleResponse` (the other 18; no `warning`), each with its numbers from that list, and `pnpm api-client:write` gives the client both. The Shopper's `findings.ts` reads every rule and its outcomes from the client (`EveryOutcome`), and `rulesInAll` is the number of rules the Shopper set words, which that check holds to the client's.
   - **`findings.ts:176`'s 16 and 2.5** were rule 8's PCIe slot of 16 lanes, which a GPU takes, and rule 15's drives of 2.5 inches, as the MVP spec's table states each rule; every outcome was given both. They are now given to those two rules' words alone (`numbersNamed`), written by `formatNumber`. They stay in the Shopper app: they are the rules' own words, not values a Part holds, and the Shopper app does not import the library.
   - **The `unworded` fallback** is gone, with its words in the three languages: the API and the Shopper app are built from one commit, whose `pnpm check` proves the committed description is the API's own and the client the description's, so the API cannot answer a rule the client does not know. An API and a Shopper app of two commits served together is the hosting work's to prevent.
   - **The fault**, below: a rule 22 added to the library's list, unworded, failed `pnpm check`.
